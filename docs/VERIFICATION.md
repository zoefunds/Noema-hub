The current local release check passed 80 direct contract tests, 4 sponsor-key safety tests, and 13 frontend tests, plus TypeScript checking, the optimized frontend build, GenVM linting of all three contracts, `pip check`, and dependency audits with no known vulnerabilities. Coverage includes complete-body inspection past the former 24,000-character limit; strict literal-boolean admissibility parsing; rejected redirects, unsupported publishers/origins, contradictory evidence, malformed replies, and prompt injection; frozen sponsor rules, FIFO handling, and queue-delay fairness (no bond forfeiture from closes_at timing alone); conflicting-evidence consensus; deadline rollback; multi-wallet exhaustion-cost bounds; misleading-but-correctly-hashed-record rejection; forged/mismatched receipts; and stateful receipt replay and duplicate-credit rejection.

Nine stateful tests in `tests/direct/test_stateful_security.py` were added to close gaps the prior suite left between "the helper function behaves correctly in isolation" and "the deployed contract method behaves correctly end to end":

- **All four `reconcile_withdrawal` outcomes are now run through the live contract method**, not just the `_payout_receipt_outcome` helper. Previously only `FAILED` (recredit) and its replay were exercised statefully:
  - `test_delivered_receipt_clears_pending_and_allows_a_later_earned_credit_to_withdraw` — a genuinely successful payout clears `pending_outbound`, marks the withdrawal `DELIVERED` without recrediting it, and then proves a later earned credit can open a distinct subsequent withdrawal.
  - `test_forged_or_mismatched_receipt_is_rejected_and_leaves_state_unchanged` — a receipt pair that fails consensus linkage (`INVALID`) reverts and leaves the withdrawal `PENDING`, `pending_outbound` untouched, and `consumed_payout_receipts` unmarked, so a legitimate retry is still possible.
  - `test_unfinalized_receipt_is_rejected_without_mutating_state` — a receipt whose child has not finalized (`PENDING`) reverts without mutating any state.
  - `test_unavailable_rpc_lookup_is_rejected_without_mutating_state` — a StudioNet RPC read failure (`UNAVAILABLE`) is rejected as retryable rather than silently treated as settled.
- **`withdraw()` itself is now exercised statefully**, not just inspected as source text:
  - `test_withdraw_blocks_a_second_pending_withdrawal_for_the_same_recipient` — a second `withdraw()` call while one is still unreconciled reverts, and the newly-arrived credit is left untouched for the next withdrawal.
  - `test_withdraw_refuses_to_send_when_hub_is_underfunded` — the solvency guard reverts before any external value message is emitted when Hub balance cannot cover total liabilities.
- **FIFO reward fairness is now enforced against the live contract, not just grepped for in source**:
  - `test_out_of_order_attestation_callback_violates_fifo_and_reverts` and `test_out_of_order_verdict_callback_violates_fifo_and_reverts` — a callback for anything but the queue head is rejected, and no bond or reward moves as a result.
- **`test_accounting_invariant_holds_through_a_full_loss_and_recapitalization`** runs the full economically consequential sequence end to end: a real backing loss on a failed payout flips `accounting_ok` to `false` and reports the exact `payout_recovery_required`, and `recapitalize_payouts` restores `accounting_ok` to `true` once the shortfall is covered — demonstrating the invariant is load-bearing, not cosmetic.

A second review round closed four further issues, each with its own stateful test:

- **Worker-callback / expire_stage mutual exclusivity.** `record_attestation` and `record_verdict` now reject outright once `now >= stage_deadline` — the exact boundary at which `expire_stage` itself becomes callable — so a late decisive callback can never race a timeout rollback for the same bond and reward. `test_late_attestation_callback_after_deadline_reverts_then_expire_stage_succeeds` and `test_late_verdict_callback_after_deadline_reverts_then_expire_stage_rolls_back` exercise both the rejected late callback and the subsequent successful `expire_stage` call in the same test.
- **`expire_dossier` deferring to in-flight adjudication.** `closes_at` (research admission) and `stage_deadline` (in-flight adjudication) are now checked separately: `expire_dossier` defers with `in-flight adjudication must resolve or expire before dossier closure` whenever a submission is still pending and its own stage has not yet timed out, even once `closes_at` has passed, so a sponsor refund can never decide that submission's outcome by a race. `test_expire_dossier_defers_while_adjudication_is_still_within_its_own_deadline` proves both the deferral and the subsequent successful closure once the stage itself times out.
- **Lifetime-submission exhaustion economics.** `RETRYABLE`/`UNAVAILABLE` (the researcher's own chosen source returning a temporary-looking HTTP status) now forfeits the bond to the sponsor instead of refunding it for free, closing the zero-cost way a researcher could previously trigger it to burn through a dossier's bounded 72-submission lifetime capacity. `test_unavailable_callback_forfeits_bond_to_sponsor_not_researcher` exercises this against the live contract.
- **Provenance semantics.** `transport_origin_verified` is no longer conflated with content-addressed assurance: it is true only for `VERIFIED_DIRECT_RESPONSE` (the transport layer was actually observed and authenticated) and false for `VERIFIED_CONTENT_ADDRESSED_ORIGIN` (no transport metadata was ever observed; the object's own immutable content-addressed identity is the independent assurance instead). `test_attestation_valid_treats_content_addressed_and_direct_response_as_distinct` proves `_attestation_valid` accepts each provenance path only with its own matching value, never the other's.

A third review round closed the remaining queue-fairness issue and extended provenance/exhaustion coverage:

- **Queue-delay fairness.** `record_attestation` no longer classifies a submission as stale (there is no longer a `STALE` outcome at all) based on `closes_at` having numerically elapsed. `seal_disclosure` already guarantees every successfully disclosed submission was revealed strictly before `closes_at` (it enforces a full `REVEAL_WINDOW` buffer before it), so a submission that is only witnessed after `closes_at` got there through FIFO queue delay, never a researcher's choice, and the fix makes that delay unconditionally free: the classification now depends only on the actual witnessing outcome (`UNAVAILABLE`, rejected, or attested), never on wall-clock timing relative to closure. Five new stateful tests exercise this against the live contract: `test_queued_submission_witnessed_after_closes_at_is_not_penalized_for_queue_delay` (a valid attestation proceeds to `VERDICT_PENDING` with the bond still fully locked, not forfeited, even though `closes_at` has long since passed), `test_decisive_settlement_still_pays_full_reward_after_closes_at_from_queue_delay` (a decisive verdict still pays the full reward plus bond under the same conditions), `test_genuine_stage_timeout_after_closes_at_still_refunds_researcher_not_sponsor` (distinguishes this from a genuine worker-side stage timeout, which still correctly refunds the researcher via `expire_stage` rather than forfeiting), `test_fifo_queue_of_submissions_disclosed_before_closure_drains_fairly` (two submissions disclosed before closure but still queued past it both settle fairly and the queue correctly advances), and `test_queue_delay_past_closes_at_never_forfeits_a_timely_disclosed_bond` (a structural test confirming `STALE` and any `closes_at` reference are both gone from `record_attestation` entirely).
- **Multi-wallet exhaustion resistance.** The lifetime cap (`MAX_LIFETIME_SUBMISSIONS = 72`) counts attempts, not distinct wallets, and is scoped per dossier, so no number of distinct attacking wallets can affect any other dossier; each one must independently post the dossier's own full bond (`max(MIN_BOND, reward // 100)`) per attempt, so Sybil-splitting the attack across wallets does not lower its total cost — the aggregate GEN at risk to exhaust one dossier is unchanged by how many wallets share it. `test_multi_wallet_exhaustion_requires_full_bond_per_attempt_and_caps_bound_displacement` runs this against the live contract: with 71 lifetime slots already consumed by 71 distinct simulated attacker wallets, a 72nd distinct wallet still gets in but only by paying the full real bond, and a 73rd distinct wallet — attacker or genuinely legitimate researcher, indistinguishably — is rejected before any bond is accepted, so a displaced wallet's cost is bounded at zero (gas aside) while every wallet that actually got in paid in full. Queue saturation is itself bounded: `MAX_ACTIVE = 24` concurrent disclosures and strictly serial FIFO processing mean an attacker occupying the full active window delays, rather than permanently displaces, a legitimate researcher's witnessing — once any attacking submission settles (forfeiting its bond on a no-evidence outcome, or being displaced itself if another submission resolves the dossier first), the queue advances and the next submission, attacker or not, is processed next.
- **Misleading-but-correctly-hashed records.** `test_misleading_attested_claim_with_quote_absent_from_body_is_rejected` runs the actual `SourceWitness` contract (not just a helper function) against a mocked document and a mocked model response that falsely claims a supporting quote exists: the record is forced to `REJECTED` with every admissibility field cleared, even though the underlying bytes were genuinely and correctly fetched and hashed. `test_attested_claim_with_quote_present_in_body_is_accepted` is its positive control. Writing these surfaced that GenVM's current web response type never exposes a final URL to the contract at all (on StudioNet or in this test harness), so `VERIFIED_DIRECT_RESPONSE` is correctly coded but not reachable today — every admissible source in this release is, in practice, the immutable content-addressed GitHub allowlist, which `docs/SECURITY.md` now states explicitly rather than leaving implicit.

### Running hosted CI from a different GitHub account

Because the blocker above is a billing/Actions-minutes problem on one specific account — not anything about the repository, the workflow, or the code — any other GitHub account can run the exact same hosted CI independently and get a real green (or red) result. The workflow needs no secrets, no paid external API, and performs no on-chain writes: both jobs only install public `pip`/`npm` packages and run local checks (lint, the direct-mode contract test suite, frontend tests, typecheck, and the production build). `gltest.config.yaml` points `direct` tests at the StudioNet RPC URL only as config metadata; the direct-mode tests themselves never make a network call.

To run it on another account:

1. **Fork the repository** into that account (GitHub → `Fork`), or add it as a remote and push the branch you want checked to a repository that account owns. Actions runs on the repository that owns the workflow file, not on the original `zoefunds/Noema-hub`.
2. **Enable Actions on the fork** if GitHub has not already done so automatically: `Settings → Actions → General → Actions permissions`, select "Allow all actions and reusable workflows," and save. A brand-new fork sometimes shows a one-time "Workflows aren't running on this forked repository" banner on the `Actions` tab — click "I understand my workflows, go ahead and enable them."
3. **Trigger a run.** Any of the following fires `quality.yml` as configured in this repo ([`.github/workflows/quality.yml`](../.github/workflows/quality.yml)):
   - push a commit to that fork's `main` branch;
   - open a pull request against any branch in that fork;
   - or, with no push/PR needed, go to `Actions → Quality → Run workflow` and trigger it manually (`workflow_dispatch` is already enabled in the workflow file) on any branch.
4. **No configuration, secrets, or `.env` file is required.** All frontend environment variables used in `npm run build`/`npm run typecheck` (`NEXT_PUBLIC_GENLAYER_RPC_URL`, `NEXT_PUBLIC_NOEMA_HUB_ADDRESS`, etc. — see [`.env.example`](../.env.example)) have working fallback defaults in [`frontend/lib/liveProtocol.ts`](../frontend/lib/liveProtocol.ts), and CI does not copy an `.env.local` file; the build succeeds without one.
5. **Read the result** on that fork's `Actions` tab: two jobs, `contracts` and `interface`, run in parallel and normally finish in one to two minutes each. A green check on both is the same hosted-CI evidence this document could not previously produce on the original account; a red check will show exactly which step failed, with the same logs any `actions/checkout`-based run produces.

This reproduces the identical check this document asks for — it does not require access to, or any changes on, the original `zoefunds/Noema-hub` account.

## Security boundaries

SourceWitness authenticates bytes, request/response binding, complete-body digest and size, exact support, and allowlisted immutable content-addressed origins. It does not turn an ordinary fetched web page into cryptographic proof of a publisher's identity or publication time; policy requiring those properties rejects the source unless the required origin authentication is available. Redirects, origin conflicts, unsupported publisher claims, and oversized or otherwise unauthenticated decisive material fail closed.

The Vercel receipt endpoint is a UI projection only. The Hub's `reconcile_withdrawal` validates finalized canonical StudioNet parent/child records directly under validator replay, including linkage, sender, recipient, amount, calldata, finality, `value_credited`, and single-use receipt consumption. A verified failure can recredit only once and withdrawals remain blocked when the resulting backing is insolvent.
